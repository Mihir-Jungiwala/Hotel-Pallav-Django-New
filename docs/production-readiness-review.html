Can this go live? Not yet — and the UI is the smallest problem.

A full read of all 6,464 lines of Python, 48 templates and 9 apps — with the findings below reproduced by actually running the code, not by eyeballing it.

Production ready 20% For a system that handles cash, guest bills and GST invoices. A blog at this standard would score higher — money raises the bar.

The app does not currently run on a Linux server at all. I logged in with a real account and the very first page after login — the Dashboard — crashed with TemplateDoesNotExist. The code asks for dashboard.html; the file on disk is Dashboard.html. Windows ignores that difference. Every production server on earth does not.

That single fact tells the whole story: this code has never been run anywhere except a Windows development machine. Six templates are referenced that cannot be loaded, a live Gmail password sits in git history, any logged-in receptionist can make themselves a superuser, and every cash amount in Revenue and Expense is stored as text — so ₹2,000 typed with a comma is being counted as ₹2 in your dashboard totals right now.

Your three questions, answered first
No Should we rewrite it in PHP? No. Not one of the 24 defects below is caused by Python or Django. They are all caused by how the code was written. PHP reproduces every one of them.
No Should we move to Laravel? No. Laravel is a fine framework, but a rewrite costs 4–6 months, throws away your working hotel domain logic, and fixes nothing you can't fix in Django in 10 weeks.
Yes Continue with Django? Yes — but not "just update the UI". The UI is roughly a quarter of the work left. The backend needs real authorisation, real money columns, and a real deployment before any of it is safe to launch.

Findings · ordered by fix priority

Seven blockers. Fix these before anyone sees this system.

Every item here was reproduced by running the code against a copy of your database. Line numbers are from commit d436ff0.

01

The app crashes on any Linux server, on the first page after login

Blocker
Dashboard/views.py:137 · Shift_Handover/views.py:127 · Revenue/views.py:209,243 · Expense/views.py:168,201,331,364,442,517,628,700 · Staff_Profile/views.py:172 · Authentication/views.py:338

Six template names in the code do not match any file on disk. Windows and macOS match filenames case-insensitively, so this works on your laptop. Linux — every hosting provider you will use — does not.

# Dashboard/views.py:137 — the landing page after every login
return render(request, "dashboard.html", context)   # file on disk is Dashboard.html
Reproduced Logged in as a real user → 302 → /Dashboard-Profile/ → django.template.exceptions.TemplateDoesNotExist: dashboard.html. Also missing entirely, not just miscased: confirm_delete.html (7 views), error_template.html (3 views), update_user_role.html, Staff__Profile_User_Update.html.
02

Any logged-in user can make themselves a superuser and delete anyone

Blocker
Authentication/views.py:75 (Registration) · :127 (Delete_User_Profile) · :312 (Update_User_Role) · :291 (User_Active_Deactive_Status)

These four views are protected by @login_required and nothing else. @login_required only asks "are you logged in?" — never "are you allowed?". A receptionist account has the same power over user accounts as the owner.

Worse, Delete_User_Profile deletes on a plain GET. That means a link or an image tag can delete a user account when an admin merely opens a page — CSRF protection does not apply to GET.

Reproduced — logged in as a non-staff, non-superuser account
  • Created a brand-new is_superuser=True account via POST /User-Registration/ — succeeded
  • Promoted itself to superuser via POST /Update-User-Role/<own id>/ — succeeded
  • Deleted another user with a plain GET /Delete-User-Profile/<id>/ — succeeded
03

Cash amounts are stored as text — your totals are already wrong

Blocker
Revenue/models.py · Expense/models.py · Shift_Handover/models.py — 14 columns

Every deposit, withdrawal and miscellaneous expense amount is a CharField, not a DecimalField. The Dashboard then runs Sum() over those text columns. SQLite silently reads the leading digits of each string and gives up at the first non-digit.

# Revenue/models.py
Deposite_Hotel_Amount = models.CharField(max_length=50)   # money as text

# Dashboard/views.py:56
.aggregate(total=Sum('Deposite_Hotel_Amount'))            # summing text
Reproduced against your schema Two rows — '1500.50' and '2,000'. Correct total: ₹3,500.50. What the Dashboard returned: ₹1,502.50. The comma turned ₹2,000 into ₹2. Anyone who has ever typed a comma has silently corrupted a daily cash total.

This also blocks the database move you will need. PostgreSQL and MySQL refuse to SUM() a text column outright — so the Dashboard will hard-crash the moment you leave SQLite, which you must do before launch.

Two consequences. First, that app password is compromised and must be revoked in the Google account today — not when you launch. Second, SECRET_KEY in public history means anyone can forge session cookies and password-reset tokens; it has to be rotated, which logs everyone out once.

With DEBUG=True in production, every crash renders a full stack trace, your settings, and your SQL to whoever triggered it. manage.py check --deploy reports 7 security warnings; these are the load-bearing ones.

05

Who performed a cash transaction is taken from the form, not the session

Blocker
Revenue/views.py:86,141 · Expense/views.py:51,95,222,270,394,468,542,660 · Shift_Handover/views.py:46

Twelve cash views read the acting staff member out of a <select> in the submitted form:

hotel_deposit_username = request.POST.get('hotel_deposite_username', '')
user_instance = get_object_or_404(User, username=hotel_deposit_username)

The logged-in user is right there in request.user and is ignored. Any staff member can record a withdrawal, an expense or a shift handover under a colleague's name, and the record will look completely legitimate afterwards.

In a cash-handling system this is the control that matters most: it is the difference between a ledger you can act on in a dispute and one you cannot. Everything about attribution must come from the session.

06

Bill totals are calculated in the browser and trusted by the server

Blocker
Bill_Master/views.py:71,146,220 (advance & refund totals) · :464–470 (bill totals) · :813 (remaining balance)

The server never recomputes a single total. It reads the finished figure out of the POST body:

total = Decimal(request.POST.get('total', '0'))  # whatever the browser sent
bill_master_hotel_total_amount = Decimal(request.POST.get('bill_master_hotel_total_amount', ''))

The arithmetic lives in JavaScript in the template. Anyone who can open developer tools — or simply has a stale page open when a rate changes — can save a bill whose total does not match its own line items, and nothing in the system will ever notice.

Same pattern on refunds: refund_total_amount arrives from the form and overwrites the advance's original Total, destroying the record of what was originally taken.

07

Two copy-paste bugs mix hotel money into food money

Blocker
Bill_Master/views.py:495 · Bill_Master/views.py:679

In the advance-balance calculation, the food branch subtracts the hotel total:

# Bill_Master/views.py:493-497
if food_advance_amount > abs(bill_master_food_total_amount):
    advance_food_balance_amount = food_advance_amount - abs(bill_master_hotel_total_amount)
    #                                                    ^^^^^ should be food

And in the bill update, the food balance is decided by the hotel mode of payment:

# Bill_Master/views.py:679
queryset.Bill_Master_Balance_Food_Amount = bill_master_food_total_amount \
    if bill_master_hotel_mod == 'Debit' else 0   # should be bill_master_food_mod

Both silently produce wrong guest balances whenever hotel and food figures differ — which is the normal case. Neither would ever raise an error. These are exactly the bugs that a single unit test per calculation would have caught, and there are no tests at all.

08

No locking on advance balances — concurrent bills double-spend

High
Bill_Master/views.py — select_for_update appears 0 times in the codebase

Two receptionists posting bills against the same advance receipt at the same time both read the old balance and both write their own result. One posting silently disappears. transaction.atomic() is used in places, but atomicity is not locking — it prevents half-written data, not lost updates.

09

Applying an advance to a bill wipes the remaining balance to zero

High
Bill_Master/views.py:559–562
advance_record.Hotel_Balance_Amount = Decimal('0') if bill_master_hotel_total_amount >= 0 \
                                      else abs(bill_master_hotel_total_amount)

The remaining balance is set to 0 whenever the bill total is non-negative — regardless of how much of the advance was actually consumed. A guest who pays ₹10,000 in advance and settles a ₹4,000 bill loses the ₹6,000 record. Refunds are also checked against the original advance rather than the remaining balance (line 251), so the opposite error is possible too.

10

Instalment payments are wired to the wrong form field

High
Bill_Master/views.py:770–774 and 793–797
bill_master_debit_hotel_amount_1 = Decimal(request.POST.get('bill_master_debit_hotel_amount_1', '0')) \
    if request.POST.get('bill_master_debit_hotel_amount', '') else Decimal('0')
#                     ^^ all four instalments are guarded by the FIRST field, not their own

Two failure modes, both live. If the base amount is filled and instalment 1 is left blank, Decimal('') raises and the whole form dies with the generic "An error occurred" message. If the base amount is blank but instalment 1 is filled, the instalment is silently discarded. Eight occurrences, hotel and food.

11

66 blanket exception handlers hide every real failure

High
Every views.py · 48 bare print() calls · no LOGGING config in settings

The dominant pattern is an entire view wrapped in try: … except Exception: return render(request, 'error_page.html'). A typo, a missing template, a database error and an unreachable mail server all produce the same blank page — for the user and for you. There is no log file, no log configuration, and no error alerting anywhere in the project, so nothing is recoverable after the fact.

Some handlers do worse than hide: several leak the raw exception text straight to the browser via messages.error(request, f'An error occurred: {str(e)}'), and Reports/pdf.py:27 dumps the entire rendered HTML into the response on a PDF failure.

12

47 of 66 views can return None and 500

High
All apps — verified by AST analysis of every view function

The common shape is if request.method == 'POST': … redirect with no else and no trailing return. A GET to any of those URLs falls off the end of the function, and Django raises "The view didn't return an HttpResponse object". Every delete view in Bill_Master, Revenue and Expense has this shape.

13

Password reset emails point at 127.0.0.1:8000

High
Authentication/Reset_Password_Email.py:22
reset_link = f"http://127.0.0.1:8000/Change-Password/{token}/"

Password reset is completely non-functional in production — every recipient gets a link to their own machine. Alongside it: the reset token is stored in plain text, never cleared after use, and Reset_Password reports "Invalid Username" for unknown users and a different message for inactive ones, which lets an outsider enumerate valid staff usernames. There is also no rate limiting on login or on reset, so both are open to unlimited brute force.

14

Uploads accept any file, of any size, and are never served

High
Staff_Profile/views.py:59–63,137–141 · Bill_Master/models.py:69 · Main/settings.py:170

Staff photos, ID documents, resumes and invoice PDFs are saved straight from request.FILES with no extension check, no content-type check and no size limit. MEDIA_ROOT also points inside a static directory (public/static) while MEDIA_URL is /media/ and no media route is registered — so uploaded files cannot currently be opened at all, and if you fix that by serving the folder statically, an uploaded HTML or SVG file becomes a stored XSS on your own domain.

Note also that User_Profile.delete() removes files from disk before the database row is deleted. If the delete then fails, the document is gone and the record remains.

15

The auto-logout middleware writes to the database on every request

High
Authentication/middleware.py:76–86 · Authentication/models.py:41

Every single request — including static file requests — runs a query for the latest activity row and then saves it, and that save runs another SELECT inside Authentication.save(). Three extra queries per request, on SQLite, which locks the whole file on write. Under any real concurrency you will see database is locked errors.

It also mutates activity_time on the row that records the original login, which means the login/logout audit trail is overwritten as the user browses. And because the hard cutoff is a fixed 10 minutes with no warning, a receptionist filling in a long bill form loses their work.

Findings · structural debt

Medium severity

16

48 templates, zero shared base template

Medium

18,292 lines of HTML across 48 files and not a single {% extends %} or {% include %}. The navigation, sidebar and styling are pasted into every page. This is why "just update the UI" is not a small job — today, changing a menu item is 48 edits, and they will drift.

17

Front-end libraries are unmaintained and unpinned

Medium

jQuery 3.3.1 (76 references) and Bootstrap 4.3.1 are loaded from stackpath.bootstrapcdn.com and code.jquery.com with no integrity hashes and no local copy. Both versions carry published CVEs (jQuery prototype pollution; Bootstrap tooltip XSS), StackPath's Bootstrap CDN is no longer a maintained service, and if either host is unreachable your app renders as unstyled text. Vendor these locally and serve them with WhiteNoise.

18

Instalments modelled as numbered columns instead of rows

Medium

Bill_Master_ADD_Bill carries Debit_Hotel_Amount, _1, _2, _3, _4 — and the same again for food, dates and payment modes. That is 25 columns doing the job of one child table, with a hard ceiling of five payments and no way to query payment history. The table is 60+ columns wide with almost every field null=True.

19

Only one Django form exists in the entire project

Medium

Reports/searchform.py defines a form that is never used. Everything else is hand-rolled request.POST.get(), so there is no validation layer at all: no required-field checks, no numeric range checks, no "amount must be positive", no re-display of a half-filled form after an error. Django's ModelForm would delete several hundred lines and add all of it.

20

Receipt and bill numbers are typed by hand

Medium

Numbers are formatted as f"{year} / {user_input}". The database uniqueness constraint will reject a duplicate, but the handler logs the failure and silently re-renders the empty form — the user sees their work vanish with no explanation. The "Excessive / {bill}" advance receipts created on overpayment have no uniqueness constraint at all (added in migration 0013, removed again in 0014), and the deletion path looks them up with .filter(...).first(), so a duplicate deletes the wrong record.

21

Repository hygiene

Medium

No .gitignore. db.sqlite3 — your actual hotel data — plus 175 compiled .pyc files are committed. requirements.txt lists both import-export and django-import-export (the first is an unrelated abandoned package). Both Authentication/views.py and Reset_Password_Email.py open with from venv import logger — an accidental import from Python's virtualenv module that happens to expose a logger object.

22

Admin panel is gated by a hardcoded username

Medium

SuperAdminOnlyMiddleware restricts /admin/ by comparing to the literal string 'SuperAdmin'. Rename that account and you are locked out of your own admin; create an account with that name and you are in. It also opens a database transaction on every single request just to run a string comparison. Meanwhile AuthenticationAdmin.save_model sets created_by and modified_by on a model that has no such fields — the assignment does nothing.

23

Name fields truncate at 20 characters

Medium

Full_Name = CharField(max_length=20) appears in Revenue, Expense and Shift_Handover, and is filled with f"{first_name} {last_name}". SQLite ignores the limit; PostgreSQL and MySQL in strict mode will reject the insert. Another thing that breaks on the day you move off SQLite.

24

Rupee-to-words conversion loses paise

Medium

amount_as_number = int(float(hotel_deposit_amount)) — the amount printed in words on every receipt is truncated to whole rupees, while the numeric amount keeps its decimals. On a printed cash receipt those two disagreeing is a real dispute waiting to happen.

In fairness

What is genuinely good here

This is not a bad idea badly conceived. There is real work in it worth keeping:

  • The domain model is right. Advance → bill → debit bill → excess-becomes-new-advance is a correct model of how a hotel actually bills corporate guests. That understanding is the expensive part, and it is done.
  • App separation is sensible. Nine apps split cleanly by business area — Revenue, Expense, Bill_Master, Shift_Handover. That is the right skeleton to build on.
  • The features are real. Denomination-wise shift handover, GST/TCS/TDS per company, staff advances against salary, PDF receipts, Indian number-to-words. Those are the things a hotel actually asks for, and they exist.
  • Django's defences are intact. All 44 forms carry {% csrf_token %}, there is no raw SQL, no |safe, no csrf_exempt. The two vulnerability classes that sink most small business apps are closed.
  • Business rules were thought about. Blocking an advance edit after it has been consumed, blocking a second refund, restoring the balance when a bill is deleted — someone reasoned about the edge cases. The implementations have bugs; the intent is sound.
The decision

PHP, Laravel, or stay on Django?

Look back at the 24 findings. Ask which of them a different language would have prevented. The answer is none. Money stored as text, totals trusted from the browser, no authorisation checks, secrets in git, zero tests — all of these are writable in PHP just as easily, and a rewrite by the same team with the same habits reproduces them faithfully.

Plain PHP No

A step backwards. You would lose the ORM, the migration system, the admin panel, CSRF protection and template auto-escaping — the four things currently keeping this app's security score above zero. You would be hand-writing the protections Django gives you for free, and finding #2 shows what happens when protections are hand-managed.

Laravel No

A capable framework — genuinely comparable to Django. But the migration is 4–6 months of full-time work: 6,464 lines of Python, 50 migrations, 48 templates and a live SQLite database, all rebuilt. At the end you have the same features you have today, plus every new bug a rewrite introduces, and the 24 problems above still need fixing because none of them were the framework's fault.

Choose Laravel only if the people maintaining this long-term are PHP developers who cannot maintain Python. That is a staffing decision, not a technical one.

Stay on Django Recommended

Roughly 10–12 weeks of focused work gets you to a defensible launch, against 4–6 months for a rewrite that starts from zero. You keep the domain model, the migration history, the data and the PDF pipeline. Django 5.1 is current and well supported, the admin gives you a free back office, and django-import-export is already wired in.

Every fix in this report is a normal, well-documented Django task. None of them require unusual expertise.

On "we just have to update the UI"

This is the part I would most want you to hear. The UI is roughly a quarter of the remaining work, and it is not the part that can hurt you. A prettier screen sitting on top of finding #3 still adds ₹2,000 as ₹2. It still lets a receptionist promote herself to superuser. It still crashes on a Linux server.

And the UI work itself is larger than it looks: with 48 standalone templates and no base file, any redesign means either editing all 48 or building the shared template layer first. Do the backend work in this order, and the UI becomes the easy, enjoyable phase at the end — on a foundation that will hold it.

The path to launch · one developer, full time

Ten to twelve weeks, in this order

The order matters. Each phase depends on the one before it, and the UI deliberately comes last.

Nowtoday · 1 hour

Stop the bleeding

Revoke the Gmail app password in the Google account. Add a .gitignore; remove db.sqlite3 and the 175 .pyc files from tracking. Treat the committed SECRET_KEY as burned. None of this waits for a sprint.

01weeks 1–3

Make it runnable and safe

  • Fix all six template references; run the whole app once on a Linux box before anything else
  • Move secrets to environment variables; DEBUG=False, real ALLOWED_HOSTS, secure cookie and HSTS settings — clear all 7 check --deploy warnings
  • Add real authorisation: a role model, @permission_required or a decorator on every state-changing view, and @require_POST on every delete
  • Take the acting user from request.user in all 12 cash views
  • Set up LOGGING to a file, replace the 48 print() calls, and narrow the widest of the 66 exception handlers
02weeks 3–6

Fix the money

  • Migrate all 14 text amount columns to DecimalField, with a data migration that cleans commas and blanks — verify the converted totals against your current records before trusting either
  • Move every total server-side; the browser may display a total, it may never submit one
  • Fix the two hotel/food copy-paste bugs (#7), the advance-balance wipe (#9) and the instalment field wiring (#10)
  • Wrap balance updates in select_for_update()
  • Move to PostgreSQL — the text columns and the 20-character name fields must be fixed first, or the move fails on day one
03weeks 5–8

Tests, then forms

Write tests for the money paths first — advance created, bill applied, partial usage, refund, overpayment becomes a new advance, bill deleted and balance restored. Those tests are what let you touch this code without fear, and they will find more bugs than this report did.

Then replace the hand-rolled request.POST.get blocks with ModelForms. This removes several hundred lines, adds validation everywhere at once, and makes the templates far smaller before you redesign them.

04weeks 8–11

The UI you actually wanted

Build base.html with the nav, sidebar and blocks, then convert the 48 pages to extend it — most will shrink by two thirds. Vendor Bootstrap and jQuery locally on current versions and serve them with WhiteNoise. Then redesign, once, in one place.

05weeks 11–12

Deploy properly

Gunicorn behind Nginx, HTTPS, collectstatic, media served outside the static root with upload type and size limits, automated nightly database backups with a restore you have actually tested, and error alerting so you hear about a crash before your staff phone you about it.

If you must go live sooner

The absolute floor is Now + Phase 01 + the money fixes in Phase 02 — call it four to five weeks. Below that you would be running a cash ledger where the totals are wrong and every user is an administrator. For an internal tool used by staff you trust, on a private network, that might be a risk you choose to take for a few weeks. For anything touching guest bills or GST invoices, it is not.
